## 1. User objective

Build a generic, deterministic CZ portal automation pipeline that:

1. Authenticates through a manual browser boundary or caller-owned Playwright
   storage state.
2. Scrapes the portal before involving an LLM, including certification groups,
   API slots, testcase tables, dependencies, statuses, controls, pagination,
   description dialogs, routes, and observable action effects.
3. Persists immutable, auditable, content-addressed evidence.
4. Normalizes that evidence without an LLM.
5. Grounds every testcase against a caller-selected repository and a read-only
   MCP documentation server.
6. Lets an LLM—not MCP—make bounded, cited decisions about HTTP requests,
   payloads, assertions, support gaps, and repository changes.
7. Applies repository changes only after an explicit plan-ID approval and
   operator-selected verification commands.
8. Deterministically renders validated execution specifications into a Postman
   Collection v2.1 and a secret-empty environment.

The immediate user priority is narrower: complete and verify the scraping of
all 1,270 testcase rows and all 1,270 testcase descriptions visible across the
portal-wide certification catalog. Do not move the run into knowledge,
grounding, synthesis, campaign application, or Postman until this gate is true.

## 2. Non-negotiable design decisions

- Browser collection is deterministic and LLM-free.
- No portal-specific selectors are hardcoded in the crawler. Portal-specific
  navigation may be represented as caller-owned strict guide data generated by
  teaching or authored manually.
- Crawl evidence is append-only. Partial runs are never resumed or overwritten;
  start a fresh run or an explicit new attempt.
- `bounded_complete` means the configured whole UI frontier was exhausted.
  `testcase_context.context_complete` is a separate, narrower gate.
- Testcase context is complete only when:
  - a declared total exists;
  - the declared total equals the number of unique testcase IDs;
  - every testcase has a description;
  - there are no testcase-field or description conflicts; and
  - the complete observation remains stable for the configured threshold.
- Authentication credentials never enter CLI flags, manifests, logs, or Git.
  Explicit storage-state exports are caller-owned credentials under ignored
  runtime paths.
- Repository and MCP evidence is untrusted input to the LLM and must be bounded,
  redacted, cited, and explicitly read.
- MCP retrieval is read-only and does not replace LLM reasoning.
- Postman rendering is deterministic and consumes only validated Phase 9 data.
- Active code must not import from `.deprecated/`.
- Do not inspect, import, or test ignored user data under `dummy_portal/` or
  `dummy-portal/` unless the project instructions are explicitly changed.

## 3. Active pipeline

```text
scraper
  -> immutable artifacts/crawls/<run-id>
knowledge
  -> normalized artifacts/knowledge/<run-id>
grounding
  -> repository/MCP artifacts/grounding/<run-id>

  -> portal-wide support matrix and reviewed shared code-change plan
synthesis
  -> validated HTTP execution specifications
optional remediation
  -> focused reviewed repository plan/apply boundary
postman
  -> deterministic Collection v2.1 and empty-secret environment
```

### Phase ownership

- `scraper/`: evidence models, artifact store, redaction, Playwright recording,
  deterministic extraction, action policy, guidance, state-graph exploration,
  authentication/session boundary, runner, and CLI.
- `knowledge/`: LLM-free semantic normalization with immutable evidence
  citations and strict coverage gates.
- `grounding/`: suffix/size/symlink-safe repository retrieval plus a bounded
  LiteLLM agent that chooses between repository search and advertised,
  code-allowlisted read-only MCP retrieval. The deterministic retriever remains
  available as an explicit compatibility strategy.
- `synthesis/`: bounded LiteLLM agentic evidence loop, strict Pydantic output,
  citation/dependency validation, progress logging, and resumable checkpoints.
- `campaign/`: repository-wide group-first support assessment and shared staged
  code/config/API change planning.
- `remediation/`: focused approved plan application with isolated verification.
- `postman/`: deterministic dependency-aware Collection v2.1 rendering.

### Implemented correction

The current uncommitted code adds portal-wide nested branch fan-out:

- `GuideTarget.css_regex` provides a bounded structural sibling matcher.
- `GuideBranchRule` represents one sibling navigation level.
- `CrawlGuide.branch_rules` remains backward compatible with old guides.
- `--teach-branch-depth N` converts the final N demonstrated route clicks
  before the testcase-info click into nested sibling levels.
- A dialog close demonstration using a link is rejected; teaching requires the
  actual button-like close control.
- `StateGraphExplorer._execute_branch_rules()` recursively discovers parent
  branch pages and catalogs their terminal slot controls without opening the
  terminal destinations.
- Parent slot-summary captures are observed first. This lets the tracker sum
  the whole catalog's declared totals before any single API slot can appear
  locally complete.
- Terminal slots are distributed across isolated, session-probed workers. Each
  worker enters an assigned slot once, captures its row table, sweeps information
  dialogs in place, and follows pagination without restoring the root for every
  testcase.
- Early completion is disabled inside individual slot sweeps. The shared
  tracker is assessed only after all cataloged slots finish.
- One shared `TestcaseContextTracker` merges all slot evidence and is the only
  early-completion authority.

For the demonstrated hierarchy, teaching is:

```text
fixed route -> certification group -> API slot -> testcase rows
                                 branch depth = 2
```

During teaching, the operator must click:

1. Fixed navigation needed to reach the catalog.
2. One representative certification group.
3. One representative API slot's Test control.
4. One testcase information/details control.
5. The actual modal close button, not an `Open full page` link.
6. Enter in the terminal to finish teaching.

### Files implementing the correction

- `scraper/guidance.py`: branch model, structural target matching, teaching
  compilation, and close-control validation.
- `scraper/explorer.py`: nested discovery, terminal-control cataloging,

  tracking.
- `scraper/runner.py`: teaching branch depth and branch-guide replay from the

- `scraper/cli.py`: `--teach-branch-depth` parsing and validation output.
- `tests/test_guidance.py`: teaching/generalization and invalid-close tests.
- `tests/test_runner.py`: CLI validation coverage.
- `tests/test_explorer_integration.py`: real-browser nested group/slot/row test.
- `tests/fixtures/dummy-portal-wide-guide.json`: checked-in guide fixture for

- `README.md`: portal-wide teaching and replay documentation.

### `cz-wide-teach-12` completed live result and performance diagnosis

The earlier inspection was premature: `cz-wide-teach-12` subsequently finalized
successfully. Its persisted manifest and coverage are authoritative:

```text
status                    completed
completion_reason         testcase context complete
elapsed                   6 hours 21 minutes
declared testcases        1270
discovered testcases      1270
captured descriptions     1270
missing descriptions      0
conflicts                 0
successful actions        2690
failed actions            0
```

This is a valid Phase 7 source and can be normalized and grounded without a
fresh completeness crawl.

The run is nevertheless a performance regression. It completed 2,616 of 2,690
actions in its first two hours, then needed more than four hours for the final
74. Nineteen actions occupied global 6-to-18-minute gaps. The old process had
loaded its modules before the memory-bounded ledger fix and retained every full
captured element tree. Its 2,691 element artifacts occupy roughly 1.1 GB, so
late-run memory and swap pressure is the leading explanation for the collapse.
The artifacts cannot prove operating-system memory pressure directly, but the
timing distribution rules out normal configured browser timeouts as the cause.

Two performance corrections now apply to fresh crawler processes:

1. The ledger retains durable `StateSnapshot` summaries and incremental
   coverage counters, releasing full `ElementSnapshot` tuples after use.
2. Action correlation uses an append-time event/network index instead of
   rescanning and Pydantic-validating the full journals after every action.

The ledger has been changed to retain only the durable `StateSnapshot` for
finished states and to accumulate element/route/frame/table/modal coverage
counters incrementally. Full `ElementSnapshot` tuples are released after their
state is stored. Regression tests cover this invariant and rebuilding the
action-correlation indexes when an existing store is opened.
